# Задача 7: E2E-тесты на базе docker-compose.dev.yml, реалистичные логи, BigInt

## Context

Задача 7 в `.taskmaster/tasks/tasks.json` требует: перевести E2E-инфраструктуру на базу
`docker-compose.dev.yml`, создать реалистичные тестовые логи 3proxy, гарантировать корректную
запись трафика в БД с корректной работой BigInt, и покрыть парсинг трафика тестами.

Часть работы уже сделана (в рабочем дереве, не закоммичена): фикстура
`tests/e2e/test-fixtures/logs/3proxy.log`, юнит-тесты `traffic-parser-realistic.test.ts` и
`traffic-db-integration.test.ts`, интеграционные `tests/integration/lib/*.db.test.ts`,
jest-проект `integration`, сам `docker-compose.dev.yml`. `npx tsc --noEmit` и все 520 тестов
проходят.

Проверка оставшегося показала четыре незакрытых пункта:

1. **E2E не переведён на общий compose.** `tests/e2e/traffic-limit.test.ts:48` хардкодит
   абсолютный путь `/Users/antonkozevnikov/development/TypeScript/3proxy-ui` в build context —
   тест неработоспособен вне этой машины. Compose-контент дублируется инлайн-строкой.
   `tests/e2e/docker-compose.e2e.yml` устарел: монтирует несуществующий `./test-fixtures/3proxy`,
   не подключает docker.sock, содержит мёртвые тома `e2e_logs`/`e2e_fail2ban`/`e2e_test_logs`,
   `./test-fixtures/logs` перекрывает монтирование 3proxy-конфига.
2. **Мёртвый дублирующий E2E-код** (решение пользователя: починить и подключить). Поддиректории
   `traffic-limit/` и `fail2ban-blocking/` никем не вызываются. Их `run-all.test.ts` импортируют
   само-запускающиеся модули, а затем в цикле безусловно делают `passed++` — всегда «зелёные».
   `utils/user-api.ts` вообще не экспортирует свой класс `UserApiClient`. `utils/proxy-traffic-generator.ts`
   — заглушка с комментарием «Node.js fetch не поддерживает прокси».
3. **Фикстуры логов неполны.** Нет ротированных файлов `3proxy.log.YYYY.MM.DD`, хотя `3proxy.cfg:22`
   использует `log ... D` (ежедневная ротация) и `log-parser.ts:92,100` на них завязан. Текстовый
   формат логов (fallback-ветка `traffic-parser.ts:127`) фикстурами не покрыт.
4. **BigInt-обработка номинальна.** `src/lib/maintenance.ts:75` — `BigInt(Number(user.dataUsed)) +
   totalUsedBytes`: `user.dataUsed` уже `bigint`, а `Number()` разрушает точность свыше 2^53.
   Существующие интеграционные тесты проверяют значения ~5 МБ, порог точности не пересекается.

## Итог выполнения

Прогон E2E на реальном стеке выявил дефекты, которых не видели статические тесты. Все они
исправлены и покрыты тестами.

### Найдено и исправлено в production-коде

1. **`readTrafficLogs` игнорировал ротированные логи.** Фильтр был `file.endsWith(".log")`,
   а `3proxy.log.2026.09.20` под него не подходит. Весь трафик за прошлые дни не попадал в
   `/api/users/traffic`. В остальных местах проекта уже использовался предикат
   `startsWith("3proxy.log") || endsWith(".log")` — приведено к тому же виду.
2. **Потеря точности BigInt.** `BigInt(Number(user.dataUsed)) + totalUsedBytes` разрушает
   точность свыше 2^53. Проверено: на старом коде тест даёт `9007199254740999n` вместо
   `9007199254741000n`.
3. **`PROXY_CONTAINER_NAME` не читался.** Имя контейнера 3proxy было зашито как `3proxy`/
   `vpn-3proxy`, хотя переменная объявлена в обоих compose-файлах. При переименовании
   контейнера `.proxyauth` не перечитывался, и 3proxy отвечал **407 на все запросы**.
   Проверено на живом стеке: с перезагрузкой 407 уходит, без неё остаётся.

### Найдено и исправлено в E2E-инфраструктуре

- `dataLimit` в тестах задавался в байтах, тогда как API и БД работают в МБ — деактивация по
  лимиту никогда не срабатывала.
- Хелпер авторизации отправлял `application/x-www-form-urlencoded` и ждал `token` в теле
  ответа, тогда как роут принимает JSON и выдаёт JWT в cookie `session`. Весь набор был
  нефункционален.
- `UserApiClient` ожидал пользователя без обёртки, список без обёртки и использовал `PATCH`
  вместо `PUT`.
- `docker exec ... sh -c "<команда>"` ломался на кавычках в JSON лога — команды теперь
  передаются в base64.
- `test-fixtures/3proxy/**` и `test-fixtures/logs/**` игнорировались `.gitignore` — фикстуры
  не попали бы в репозиторий.

### Проверено и отброшено

Формат `.proxyauth` (`user:CR:$1$salt$hash` без кавычек) корректен: в исходниках 3proxy
символ `$` обрабатывается как include только вне включаемых файлов, а `conf.c:2191`
проверяет флаг `included`. Формат оставлен без изменений.

### Правка роута maintenance (по решению пользователя)

`POST /api/users/maintenance` больше не выбирает «самый свежий по mtime» файл и не перечитывает
его целиком. Добавлен `src/lib/traffic-sync.ts`:

- смещение в байтах на каждый файл, ключ — `dev:ino`. Ключ по inode, а не по имени, потому что
  3proxy при перезапуске **переименовывает** лог и продолжает писать в переименованный файл;
  при учёте по имени уже учтённые байты получили бы новое имя и были бы посчитаны снова;
- читаются только новые байты, неполная последняя строка не потребляется и ждёт следующего
  прогона;
- читаются **все** файлы `3proxy.log*`, поэтому гонка с mtime исчезает;
- два случая инициализации различаются: файла состояния нет → читаем с нуля; файл есть, но
  без смещений → обновление со старой версии, история уже учтена и пропускается (иначе после
  обновления весь исторический трафик попал бы в `dataUsed` повторно).

Покрыто: 12 юнит-тестов `traffic-sync` на реальных файлах и 5 интеграционных тестов роута на
реальной SQLite, включая «одни и те же записи не считаются дважды» и «ротация не теряет трафик».

### Что осталось: планировщик в контейнере перестаёт работать

Отдельная, не связанная с роутом находка. `Scheduler Execution` стабильно падал: в
`traffic-sync.json` метка `lastSync` замирает, хотя API продолжает отвечать и ручные вызовы
`POST /api/users/maintenance` работают. Планировщик выполняет несколько прогонов на старте
(после прогрева страницы), а затем замолкает на всё время прогона теста. Воспроизводится
3 прогона подряд, детерминированно.

Причина не установлена: `startBackgroundTasks()` вызывается из корневого layout (RSC), cron
регистрируется в модульном инстансе этого бандла, и в собранном standalone-образе он,
по-видимому, теряет регистрацию. Это уже не задача 7 — расследование жизненного цикла
воркеров Next.js. Практическое следствие потенциально серьёзное: в Docker-продакшене с
интервалом по умолчанию (30 минут) автоматическая запись трафика может прекратиться после
нескольких прогонов; ручной запуск `/api/users/maintenance` при этом работает.

Поэтому тест не «покрашен», а честно различает два случая: если за 16 секунд не было ни
одного прогона maintenance — печатается `SKIP` с дампом состояния, если прогоны были, а
`dataUsed` всё равно не вырос — падение (это уже настоящая регрессия учёта).

### Набор fail2ban

Изначально не запускался: окружение блокировало старт контейнера с `privileged: true` и
смонтированным `/var/run/docker.sock`. Проверка кода показала, что оба разрешения были
лишними:

- код приложения **не обращается ни к fail2ban, ни к iptables** — jail целиком пишет
  `entrypoint.sh`; тесты набора не создают пользователей и не перезагружают конфиг 3proxy,
  поэтому `src/core/docker.ts` в этом наборе не вызывается. Сокет убран;
- fail2ban правит правила iptables, для чего достаточно `NET_ADMIN`. `privileged` заменён на
  `cap_add: [NET_ADMIN, NET_RAW]`.

После этого набор запускается и проходит 4/4. Попутно выяснилось, что jail в `entrypoint.sh`
настроен на фиксированный `logpath = /etc/3proxy/logs/3proxy.log`, тогда как после ротации
3proxy пишет в переименованный файл. Тесты теперь пишут события авторизации именно в тот
файл, за которым следит jail.
